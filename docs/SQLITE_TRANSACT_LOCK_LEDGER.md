## Notes

- `okto-pulse-core` was clean on `main` at start. `okto-pulse` had a pre-existing untracked `docs/pulse-simplification/IMPLEMENTATION_LEDGER.md`; leave it intact.
- The legacy unrelated-board fencing test remains valid for the old adapter default; Community runtime enables the durable protocol. The native Spec test pauses graph commit while a different Board commits to the same SQLite database in under 10 seconds (test threshold); it then verifies normal completion.
- Native Grafx receipt test passed after closing and reopening the graph. Provenance refusal test passed when commit history is unavailable. Core and Community changed interfaces compile.
- SQLite writer diagnostics now start timing at explicit `BEGIN IMMEDIATE`, before the request's first DML. The event reports commit/rollback requested; it is a lower bound, not a proof of durable completion.
- An exact current SQLite schema fingerprint rejects ad-hoc table additions; any new table requires a governed schema conversion or a journal outside the source database. The existing queue is already source-transactional.
- Validation: Community focused worker/Grafx/lock suite 101 passed; journal/worker fencing suite 41 passed after protocol validation; routed graph transaction suite 11 passed; Board erasure 4 passed; routed lifecycle and worker runners 34 passed; final Board erasure and runners rerun 22 passed; native 570 KB Spec journal, unrelated SQLite writer, and post-commit recovery integration 1 passed twice. Core directly affected suite 27 passed; worker run-loop and resilience suite 28 passed. Both 0.4.1 wheels built; Community rebuilt after the final adapter changes. The application suites used the matching 0.4.1 wheel metadata on the pytest path because the local Python environment still advertises a different installed pair.
- An unrelated pre-existing Core test expects an exact rebuild source set without `sprint`; another uses a plain `object()` as a DB for a source path requiring `get()`. These fail in the selected Core suite and are not caused by this protocol.
- Community release-gate unit tests initially passed 6/7; the seventh required an explicit Grafx source checkout. With `OKTO_E2E_GRAFX_REPO` set to the local `okto_grafx` 0.0.7 checkout, the installed gate passed after its cold-start timeout was adjusted from 60 to 120 s. Individual Core/Community 0.4.1 wheels also built successfully.
- The persistent kernel rendezvous sits outside the board directory so Windows board erasure can remove the graph directory while the guard is held; direct test passed.
- The native integration injects an exception after Grafx commit but before SQLite ACK and verifies recovery with the actual audit adapter. A separate native receipt test verifies reopen. An initial benchmark with one 570 KB `context` value correctly failed Grafx's 65,536-character per-value limit; the passing workload distributes approximately 570 KB across criteria and context. It does not simulate a physical power cut.
- Rollout requires all 0.4.0 processes to stop before starting the paired 0.4.1 Core and Community distributions. Old workers do not understand the journal, so mixed-version workers must not share a live database. The existing distribution compatibility gate checks the paired versions within one process; it cannot fence a separate old process.
- Implementation choice relative to the initial plan: the existing transactional queue supplies source intent and claim lineage; the append-only `domain_events` table supplies the operation journal, avoiding a physical schema conversion. The native Grafx commit-history metadata supplies the graph receipt. Separate desired/applied revision columns were unnecessary for the proven queue CAS semantics. A protocol-1 marker now fails closed during recovery, but no new binary can force already-running 0.4.0 workers to honor it. The rollout requires stopping those workers; production latency and physical power-cut tests remain release qualification work.
